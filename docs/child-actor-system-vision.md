# SpringEngine Child Actor Hierarchy Vision

SpringEngine should support hierarchical actors where any actor can become a child of another actor, and children can themselves own children at arbitrary depth.

This system provides composition-level grouping for gameplay objects (weapons attached to characters, UI anchors in world space, multipart props) without requiring scripts to manually mirror parent movement.

## Goals

- Support `parent` links directly in actor config (`*.dat.conf`).
- Allow nested hierarchy depth (`parent -> child -> grandchild -> ...`).
- Ensure child actors are affected by parent transform changes.
- Ensure parent rigidbody movement affects descendants.
- Keep hierarchy deterministic and validated during scene load.

## Config Contract

Child actors are declared with a `parent` field on the actor record.

```toml
[[Actors]]
id = "player"

[Actors.Transform]
position = [0.0, 0.0, 0.0]

[[Actors]]
id = "player_weapon"
parent = "player"

[Actors.Transform]
position = [20.0, -4.0, 0.0]

[[Actors]]
id = "weapon_muzzle"
parent = "player_weapon"

[Actors.Transform]
position = [12.0, 0.0, 0.0]
```

## Hierarchy Semantics (First Implementation Pass)

- `parent` references another loaded actor by `id`.
- Parent links are validated after scene instantiation.
- Cycles are invalid and fail scene load.
- Self-parenting is invalid and fails scene load.
- Missing parent id is invalid and fails scene load.
- Child transform inheritance is applied every frame using parent transform delta from previous frame.

### Transform Inheritance

Per frame, each child receives parent delta:

- `position += parent_delta_position`
- `rotation_euler += parent_delta_rotation`
- `scale *= parent_scale_ratio`

This means:

- Script changes on parent transform affect children.
- Rigidbody motion on parent affects children.
- Child local script/physics motion remains additive in world space.

## Runtime Validation Rules

Hard-fail scene load when:

- `parent` is not a non-empty string.
- `parent` points to missing actor.
- Actor parents itself.
- Parent graph contains any cycle.

## Runtime Data Model

Actor runtime state includes:

- `has_parent`
- `parent_id`
- `previous_transform` (for frame-to-frame delta propagation)

No hard parent pointer is persisted; parent references are resolved by actor id to remain safe when registry storage compacts after destroys.

## Update Order

1. Script/component updates.
2. Rigidbody integration.
3. Parent delta propagation (recursive, parent-first).
4. Collision resolution.
5. Camera sync / draw.
6. Snapshot `previous_transform` for next frame.

This ordering guarantees children inherit movement generated by parent scripts and physics in the same frame.

## Destroy / Lifetime Behavior

- Destroying a parent does not automatically destroy descendants in first pass.
- If parent disappears, child remains at its current world transform and no longer inherits updates.
- Future policy options can add cascade destroy or automatic reparenting.

## Script API Notes (Current Behavior)

- Existing script transform APIs continue to operate on actor transform fields.
- Parent influence is applied by runtime after updates.
- This keeps compatibility with existing scripts while enabling hierarchy-based motion.

## Future Extensions

- Optional `inherit_position`, `inherit_rotation`, `inherit_scale` flags.
- Local-vs-world transform API in Lua.
- Explicit child iteration and reparenting APIs.
- Parent destroy policies (`keep_world`, `cascade_destroy`, `reparent_to_root`).
- Editor-friendly hierarchy diagnostics.

## Summary

The child actor hierarchy system introduces deterministic, validated parent-child relationships in SpringEngine actor configs and applies parent transform/rigidbody movement to descendants each frame. This enables nested actor composition immediately while preserving existing script/component workflows.
